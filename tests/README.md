# tests

Test programs that run headless in the PSoXide emulator.

| Folder | What it checks | How to run |
|---|---|---|
| `hello/` | The `psoxide-c` runtime: startup, the debug console, `tty_printf` | `psoxide-c/build.sh build/hello.exe -- tests/hello/main.c`, then launch with `--stop-on-tty DONE` |
| `qdup-physics/` | QD Up's fixed-point ball physics (`FIXBALL.C`) against shots recorded from NMS's 1996 build. One executable per recorded shot and variant: `_orig` uses the 1996 build's cushion tables and logic, `_fixed` the corrected tables and the cushion clamp. Each prints every ball's state per physics call | `tests/qdup-physics/build.sh`, then `python3 tools/qdup_compare.py SHOT...` (the shots are in the 1996 data's oracle folder) |
| `psyq-libm/` | The Psy-Q layer's maths functions (`sqrt`, `sin`, `atan2` and the rest) against the host's, result by result | `tests/psyq-libm/build.sh && tests/psyq-libm/check.py` |
| `psyq-snd/` | The layer's libsnd. `main.c`: loads one of 360X's sound banks, keys a note the way 360X's ship demo does, and measures the emulator's audio output (pitch, length, pan). `seq.c`: plays OPTPA.SEQ on the OPTIONS bank with the calls NMS's March 1996 build makes; `check_seq.py` runs that 1996 build (Sony's libsnd) and `seq.exe` and compares the voice registers set at each key-on and the loudness of the two outputs | `tests/psyq-snd/build.sh && tests/psyq-snd/check.py && tests/psyq-snd/check_seq.py`, with the 360X tree served over the PC link; both run muted, audio to WAV files only |
| `psyq-card/` | The layer's memory-card directory walk (`read_dir`, `find`, `chain` in `psyq/src/card.rs`) against psx-mc's `DirOptions::BIOS` forms on random directory images: bad checksums, wildcards, broken links, loops, an unformatted header; counts the device reads too | `tests/psyq-card/run.sh` (host, needs `build/psoxide` from a layer build) |
| `gameplay/` | The games are played through the pad the emulator presents (the layer's own poll), in three setups: a digital pad, a DualShock in analog mode with the direction pad, and the same with the left stick. `x360.sh`: Mission 1, one assertion per control on game variables (Left and Right turn the craft opposite ways, Cross burns fuel and pushes against gravity, Fire starts a shot, R1 and L1 change the weapon, Select opens the menu and Start on RESUME closes it, Start pauses) with a frame each; `x360-newlife.sh`: after a life ends (test disc t-newlife: its shields go to 0 at game cycle 1100) the next life starts at Mission 1's start position; `x360-craft.sh`: the craft rules restored from the PC and Saturn versions (thrust with an empty gauge and the gauge's rate, the craft stays on a 960 x 960 and a 1280 x 720 map, each of the nine missions starts it on an empty pixel, it never stands on a solid pixel and leaves its start in every mission), its input scripts started from each mission's own start; a random thrust script may be trapped by a narrow start (Mission 5's was, in one build), so the check that the craft leaves its start falls back to a sweep of ten quarter-turns before it fails; `x360-laser.sh`: the laser creature's beam on a test disc (no line before the craft is in range, five lines a cycle once it is); `qdup.sh`: the one QD Up disc in both views from the boot, through the choice screen, to a struck shot (Left and Right change the cue angle, Cross with Down and Up strikes, the balls move, the turn passes), plus the choice screen's buttons and L2+R2 switching the view in the game | `tests/gameplay/x360.sh build/360x-cd OUT`, `tests/gameplay/x360-newlife.sh build/t-newlife OUT`, `tests/gameplay/x360-craft.sh build/360x-cd OUT`, `tests/gameplay/x360-laser.sh build/360x-laser OUT` (a disc built with `X360_CFLAGS='-DX360_TEST_WARP=100 -DX360_TEST_WARP_EVERY=900 -DX360_TEST_WARP_HOLD=700 -DX360_TEST_WARP_NAMES=109 -DX360_TEST_WARP_DX=26 -DX360_TEST_WARP_DY=0'`), `tests/gameplay/qdup.sh build/qdup-cd OUT` `x360-pod.sh` (a test disc, `-DX360_TEST_POD_X=650 -DX360_TEST_POD_Y=430`, one pod in Mission 6): in all three setups a Triangle press takes the pod, the craft carries it on the rope and a second press drops it and it falls. `x360-pickup.sh` (three test discs, `-DX360_TEST_PICKUP=0|1|2`): a pick-up put at the craft fills the fuel, fills the shields, or reverses gravity. `x360-tele.sh` (two test discs, `-DX360_TEST_TELE=1|2`): a teleporter put at the craft sends it to another mission. `x360-weapons.sh` (a test disc, `-DX360_TEST_FIRE` and the warp flags in the script): each weapon fired through the pad, with a control. `qdup-fields.sh build/qdup-cd OUT GATE`: QD Up's option screen draws both of its fields: neither field holds the title picture after its first frames, a caption change and a closed panel, the two fields agree there, and the 2D or 3D choice and PLEASE WAIT hold one picture on both fields (runs `qdup-fields.toml` in the PSoXide gate and compares the two fields of its frames; the test build `QDUP_TEST_ONE_FIELD` fails it). |

The 360X scripts' boot presses skip the boot splash with their first press (`x360-craft.sh` adds one press for it, so the later timed presses meet the screens they were written for). QD Up's presses start at tick 1000, after the splash.

`qdup-physics/gen/` holds the recorded start states, converted to C by `tools/qdup_gen_state.py`.

The QD Up 2D route in `tools/qdup_run.py` (the scripted shots) is sensitive to the boot's timing rather than the game's logic. Two builds that differ only in code layout first diverge at route tick 945 (the video frame counter is one ahead, before any button is pressed). From there every timed press lands on another game frame, so the first shot's strength and the tick count differ (804d120: 8,337 ticks, `max_vx` 6.79; b2540fc: 8,408 and 7.22; with the debug gate: 8,346 and 6.79). Judge the route by the heap block peaks, which do not move, and by `tests/gameplay/qdup.sh`, which asserts the controls and not the shot.

A note on frames from test discs: the rectangular blocks that did not join their neighbours in Mission 1's frames were not the map's art. They were map from elsewhere, left in the scroller after the start view jumped onto the craft (docs/DECISIONS.md, "The first screen is loaded where the view lands"). An earlier comparison missed this because it matched two frames that both showed the same stale blocks.
